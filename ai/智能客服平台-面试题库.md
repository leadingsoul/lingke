# Group22 智能客服平台 — 面试题库（专业版）

> 项目：电商多端智能客服平台（FastAPI + Redis + MySQL + WebSocket + 多前端）
> 覆盖技术要点：AI 意图识别 / RAG / 情感分析 / 工单自动分类 / Agent 自进化 / WebSocket 架构（单例连接池 / 心跳 / 指数退避重连 / 假死检测）/ Redis 令牌黑名单与在线状态

## 一、简单题（10 题）

### Q1. FastAPI 相比于 Flask/Django 的优势是什么？你项目中是如何利用这些特性的？
**回答要点**：基于 ASGI，原生支持 `async/await` 和 WebSocket；Pydantic 自动校验请求/响应并生成 OpenAPI 文档；依赖注入（`Depends`）管理鉴权与数据库会话。
**代码位置**：[config.py 使用 Pydantic BaseSettings](file:///d:/software/project/lingke/backend/app/core/config.py#L1-L89)｜[deps.py 依赖注入](file:///d:/software/project/lingke/backend/app/core/deps.py)

### Q2. 为什么选用 MySQL + aiomysql 异步驱动？同步连接和异步连接有什么区别？
**回答要点**：异步驱动不阻塞事件循环，高并发下不会因数据库 IO 卡住其他请求；连接池由 `aiomysql` 管理。数据一致性要求高的业务（订单、工单）用关系型 MySQL 更合适。
**代码位置**：[config.py DATABASE_URL](file:///d:/software/project/lingke/backend/app/core/config.py#L58-L66)

### Q3. Redis 在项目里承担了哪些职责？
**回答要点**：令牌黑名单（`blacklist:token:*`）、登录失败锁定计数、短信验证码存储及过期、在线状态/在线用户实时维护（配合 WebSocket）。
**代码位置**：[config.py REDIS_URL](file:///d:/software/project/lingke/backend/app/core/config.py#L73-L75)

### Q4. JWT 由哪三部分组成？你的 access token 和 refresh token 是如何约定的？
**回答要点**：Header.Payload.Signature；access token 有效期短（默认 120 分钟），refresh token 7 天，通过 token 中 `type` 字段区分。
**代码位置**：[security.py create_access_token/create_refresh_token](file:///d:/software/project/lingke/backend/app/core/security.py#L29-L52)

### Q5. WebSocket 相比 HTTP 轮询/长轮询有何优势？
**回答要点**：全双工长连接，服务端可主动推送，无需客户端反复轮询，适合消息、会话状态、工单变更的实时通知，显著降低延迟与带宽开销。
**代码位置**：[router_ws.py 推送实现](file:///d:/software/project/lingke/backend/app/api/v1/router_ws.py#L57-L83)

### Q6. 你如何做 WebSocket 连接认证？为什么用 query 传 token 而不是 Header？
**回答要点**：通过 `?token=` query 参数传 JWT，解码后校验为 access token 且含合法 `sub`/`role` 才 accept；因为浏览器 WebSocket API 无法自定义请求头。
**代码位置**：[router_ws.py websocket_endpoint](file:///d:/software/project/lingke/backend/app/api/v1/router_ws.py#L143-L190)

### Q7. 什么是 L1/L2/L3 三级接入？它是怎么被决定的？
**回答要点**：L1 纯 AI 自动回复（简单咨询）、L2 AI 主导 + 人工可介入（较低置信度/需追问）、L3 高风险或高情绪强制人工接入。由意图识别引擎输出的 `level` 结合情感分析共同决定。
**代码位置**：[intent_engine.py classify](file:///d:/software/project/lingke/ai/ai_engine/intent_engine.py#L68-L76)

### Q8. 什么是 RAG（检索增强生成）？解决了什么问题？
**回答要点**：先从知识库检索相关知识片段，再注入 prompt 让 LLM 基于片段生成答案，解决 LLM 幻觉和知识陈旧问题，把企业私有知识注入模型。
**代码位置**：[rag_engine.py retrieve + generate_reply](file:///d:/software/project/lingke/ai/ai_engine/rag_engine.py#L213-L273)

### Q9. 你们的 AI 引擎为什么全部做了 Mock 模式？它是怎么工作的？
**回答要点**：便于无 API Key 时开发调试与 CI 测试；当 LLM 抛出异常时自动降级到关键词/规则匹配的 `_fallback_*` 方法，保证功能不中断。
**代码位置**：[intent_engine._fallback_classify](file:///d:/software/project/lingke/ai/ai_engine/intent_engine.py#L94-L116)｜[ticket_classify_engine._fallback_classify](file:///d:/software/project/lingke/ai/ai_engine/ticket_classify_engine.py#L122)

### Q10. 前端平时展示的"提问建议"是怎么生成的？
**回答要点**：优先用 LLM 根据用户消息和意图上下文动态生成 3-5 个追问，异常时按意图等级返回固定建议并结合知识库标题。
**代码位置**：[chat_service._run_suggestions](file:///d:/software/project/lingke/backend/app/services/chat_service.py#L192-L255)

## 二、中等题（8 题）

### Q11. 你们的 WebSocket 客户端为什么要做成全局单例？怎么保证各部分组件的消息分发？
**回答要点**：多个组件共用一条连接，避免重复建连浪费；通过模块级 `_ws` 变量 + `_handlers Map<event, handler[]>` 实现事件发布订阅，组件用 `on/off` 订阅、卸载时清除。
**代码位置**：[useWebSocket.ts 单例与分发](file:///d:/software/project/lingke/frontend/cs-end/src/hooks/useWebSocket.ts#L31-L52)

### Q12. 请解释 WebSocket 心跳机制（ping/pong）的具体流程。
**回答要点**：服务端每 30s 发送 `ping` 事件，客户端回复 `pong`；服务端用 `asyncio.Event` 等待 15s，超时未收到则主动断开连接并清理连接池，防止僵尸连接拖垮资源。
**代码位置**：[router_ws.py _heartbeat_loop](file:///d:/software/project/lingke/backend/app/api/v1/router_ws.py#L89-L131)

### Q13. 什么是"连接假死"？你是怎么检测的？
**回答要点**：TCP 连接还建立着但实际已无法通信（断网/挂起）。客户端 90s 内收不到任何 ping 或业务消息即判定假死，主动 `cleanup` 并调度重连，而不是被动等待。
**代码位置**：[useWebSocket.ts PING_TIMEOUT_MS 与 _resetPingTimer](file:///d:/software/project/lingke/frontend/cs-end/src/hooks/useWebSocket.ts#L44-L63)

### Q14. 断线重连的"指数退避"是怎么实现的？上限是多少？
**回答要点**：初始延迟 3000ms，重连失败延迟 ×1.5 增长，上限 `MAX_RECONNECT_DELAY = 30000ms`；连接成功或打开后重置为 3000ms。
**代码位置**：[useWebSocket.ts _scheduleReconnect 与 onclose](file:///d:/software/project/lingke/frontend/cs-end/src/hooks/useWebSocket.ts#L105-L124)

### Q15. Redis 令牌黑名单是怎么做的？为什么能实现"登出即失效"？
**回答要点**：登出时调用 `revoke_token`，取 token 的 `exp` 与当前时间差算 TTL，写入 `blacklist:token:{token后32位}`；鉴权中间件校验时先查黑名单命中即拒绝。黑名单键取 token 尾部，登出后旧 token 立即失效。
**代码位置**：[auth_service.revoke_token](file:///d:/software/project/lingke/backend/app/services/auth_service.py#L341-L355)

### Q16. 意图识别引擎优先走 LLM，异常时如何降级保证系统可用？
**回答要点**：`classify` 先尝试 LLM 分类，异常则走规则关键词匹配（投诉/咨询/闲聊），并设置保守置信度，避免简单问候被误判为高风险转人工。
**代码位置**：[intent_engine.classify + _fallback_classify](file:///d:/software/project/lingke/ai/ai_engine/intent_engine.py#L68-L116)；[chat_service 后端兜底](file:///d:/software/project/lingke/backend/app/services/chat_service.py#L70-L92)

### Q17. LLM Gateway 实现了哪些稳定性能力（多模型切换/重试/降级/限流）？
**回答要点**：统一封装模型配置项（base_url、温度、max_tokens、超时、最大重试）；支持同步 `chat_sync`、异步 `chat`、流式 `chat_stream`；错误时按配置重试，主模型不可用则切换到备用模型，完全不可用时上层引擎走规则降级。
**代码位置**：[llm_gateway.py LLMConfig/chat 系列](file:///d:/software/project/lingke/ai/ai_engine/llm_gateway.py#L19-L182)

### Q18. 你如何在前端避免 WebSocket 事件回调造成内存泄漏？
**回答要点**：每个订阅的组件在卸载时调用 `off(event, handler)` 从 `_handlers` 移除自己，避免已卸载组件仍收到消息导致事件回调堆积；`beforeunload` 时全局 `_disconnect` 清理。
**代码位置**：[useWebSocket.ts off 与 beforeunload](file:///d:/software/project/lingke/frontend/cs-end/src/hooks/useWebSocket.ts#L178-L211)

## 三、困难题（8 题）

### Q19. 从架构上看，如何保证 AI 引擎（纯包）与后端（服务）解耦？为什么这样设计？
**回答要点**：AI 侧 `group22-ai` 作为独立 Python 包（`setup.py`）通过 git dependency 安装，后端以类级惰性单例 `_gateway/_intent_engine/...` 封装引用。好处是 AI 引擎可独立开发/测试/发布，后端只需面向引擎 API 编程；坏处是需要管理版本兼容。属典型的服务-引擎分层设计。
**代码位置**：[ai/setup.py 包配置](file:///d:/software/project/lingke/ai/setup.py)｜[chat_service 懒加载单例](file:///d:/software/project/lingke/backend/app/services/chat_service.py#L21-L60)

### Q20. 请描述"用户发消息 → AI 回复"的完整链路，涉及哪些引擎与存储。
**回答要点**：前端 WebSocket 推 `new_message` → ConnectionManager 路由 → chat_service 依次调用 `_correct_typos`（错别字纠正）→ `_run_intent_engine`（意图/等级）→ `_run_rag_engine`（知识检索，更新命中计数）→ `_run_ai_reply_generation`（答案生成）→ DialogManager 维护上下文 → 结果写库并 WebSocket 推回。异常层层降级。
**代码位置**：[chat_service AI 封装链路](file:///d:/software/project/lingke/backend/app/services/chat_service.py#L67-L190)

### Q21. RAG 的检索/重排/答案合成为什么要分成三个步骤？说说你实现的三级召回策略。
**回答要点**：检索保证召回率（粗召回 top_k=15，关键词 + n-gram `_extract_keywords`），重排用 LLM 语义相关性提升精度（`validate_retrieval`/`_llm_validate`），合成阶段把知识片段注入 prompt 生成有依据的回答，并对命中知识 `hit_count` 计数，反哺知识库排序。三级避免"一次检索定胜负"导致漏检或噪声干扰。
**代码位置**：[rag_engine 检索/校验/生成](file:///d:/software/project/lingke/ai/ai_engine/rag_engine.py#L200-L537)

### Q22. "Agent 自进化闭环"指的是什么？会话沉淀到知识库的过程如何保证质量？
**回答要点**：会话结束 → `summarize_conversation` 总结 → 提取 FAQ（`extract_faqs_from_summary`）→ 与已有知识去重（`dedup_faqs`，规则 tokenize 去重）→ 生成对策草稿 → 审核通过后才写入知识库。不是"聊天内容直接入库"，而是经总结/清洗/去重/审核形成的沉淀，避免污染 RAG 知识库。
**代码位置**：[evolution_engine.py 自进化流程](file:///d:/software/project/lingke/ai/ai_engine/evolution_engine.py#L31-L311)

### Q23. 在大并发场景下，单机 `active_connections` 字典作为连接池会有哪些问题？如何横向扩展？
**回答要点**：单进程内存态字典在分布式部署下各节点连接彼此不可见，无法跨节点精准推送。需要把连接注册信息（user_id→node）放到 Redis，配合消息中间件（如 Redis 发布订阅 / Kafka / 消息队列）做跨节点广播，由各节点只推送自己持有的连接，实现水平扩展。
**代码位置**：[ConnectionManager 本地连接池](file:///d:/software/project/lingke/backend/app/api/v1/router_ws.py#L13-L47)

### Q24. 情感分析如何识别"高风险"用户？它与工单分类如何联动？
**回答要点**：`SentimentEngine.analyze` 输出正/中/负面及强度，`_calc_risk_level` 结合情感与强度算出风险等级，`detect_high_risk` 做高风险判定；当意图+情感命中的高风险会驱动 L3 强制转人工，同时工单分类引擎据此加快升级、调整优先级与责任归属。
**代码位置**：[sentiment_engine 分析与风险](file:///d:/software/project/lingke/ai/ai_engine/sentiment_engine.py#L54-L114)；[ticket_classify_engine](file:///d:/software/project/lingke/ai/ai_engine/ticket_classify_engine.py#L84-L122)

### Q25. LLM 输出是不可控的，你是如何清洗并保证前端渲染干净的？
**回答要点**：`_clean_markdown_artifacts` 清洗 LLM 输出：去掉 markdown 标题符号、代码块标记、孤立不成对的 `**`、残余 `*` 斜体符号，同时保留有效的粗体和有序/无序列表，避免前端渲染出乱码。
**代码位置**：[chat_service._clean_markdown_artifacts](file:///d:/software/project/lingke/backend/app/services/chat_service.py#L146-L191)

### Q26. 鉴权中间件如何与 Redis 黑名单 + 登录锁定结合，形成完整的安全闭环？
**回答要点**：JWT 无状态签发 → 鉴权时检查黑名单（登出即时失效）；登录失败用 Redis `incr` + 过期时间计数，5 次失败锁定 30 分钟（`check_login_lockout`/`_record_login_failure`）；配合 AES 手机号加密存储、接口限流（`RATE_LIMIT_*`），形成认证-授权-风控的闭环。
**代码位置**：[auth_service 锁定与黑名单](file:///d:/software/project/lingke/backend/app/services/auth_service.py#L341-L370)；[security 加密](file:///d:/software/project/lingke/backend/app/core/security.py#L61-L74)；[config 限流配置](file:///d:/software/project/lingke/backend/app/core/config.py#L66-L68)
